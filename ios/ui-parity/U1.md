# U1: camera HUD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use the `subagent-driven-development` skill (recommended) or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the camera screen of the iPhone app has the shape of Android's `MainActivity`: two translucent bands over a full-bleed preview, a shutter and mark-only controls, a SKIP button of its own, the start-position coach, the launch view, and no status bar or home indicator.

**Architecture:** what each control is at each moment, and the start figure's motion, are decisions with no platform in them, so they go to CindyCore (`HudControls`, `HudSpeech`, `StartPoseMotion`) and are tested on Linux. The SwiftUI layer draws them: a new `CameraHud.swift` holds the two bands and `HudButtons.swift` the glass circle and the shutter, both built only from `Palette`, `CindyType` and `CindyIcon`. `ContentView` keeps the camera, the sheets and the first-run plumbing, and calls the HUD.

**Tech Stack:** SwiftUI (iOS 17.0), CindyCore (XCTest on Linux), XCUITest with `-CindyReplay`.

**Spec:** `ios/ui-parity/PLAN.md` (decisions 1 to 8 and the global constraints) and `docs/adr/0003-ios-follows-android-ui.md`. The Android sources, read on `origin/main` at `bc81b76`: `activity_main.xml`, `MainActivity.kt` (`renderControls`, `primary`, `toggleRun`, `onSkip`, `renderChips`, `updateCoach`, `describeControls`, `keepHudClearOfSystemBars`), `StartPoseView.kt`, `LaunchView.kt`, `CountdownView.kt`, `HudTour.kt`.

**Branch:** `ios-ui-u1-camera` from `origin/main`. The pull request targets `main`. This session's branch name is the one it was given; the pull request says so.

## Global Constraints

Everything in the master plan's global constraints, in particular:
- iOS 17.0 is the floor. No glass blur, no system materials. Colours only from `Palette`, type only from `CindyType`, icons only from `CindyIcon`.
- Words are copied verbatim from the Kotlin. Nothing in code or comments names a phase.
- **`Color.accent`, `Color.dim`, `Color.warn`, `Chip`, `PrimaryButton` and `GhostButton` stay defined in `ContentView.swift`.** The menu, the session page, Progress and the placement guide still use them until the cleanup phase. This phase stops using them on the camera screen and deletes none.
- **The analysis frame stays as it is.** The capture session, the Vision crop and the film are untouched; the bands are an overlay. The film's own burned-in skeleton and text colours are not this phase's.
- The accessibility identifiers `CindyTrackerUITests` uses keep working, or the test changes in the same commit.
- A button that is a mark has a spoken name, and its identifier is the Android view's id: `btnStart`, `btnSkipExercise`, `btnEnd`, `btnFlip`, `btnUndo`, `btnAddRep`, `btnMenu`, `btnRec`.

## Review Focus

- **The largest Dynamic Type size.** At `accessibility-XXXL` the shutter, SKIP, END and the rep count are on screen and hittable, and the two bands do not overlap. Test in Task 4.
- **A long status line.** "Movement barely registers — raise the phone or step back" at the largest size wraps or shrinks and is never cut to nothing, and does not push the clock off the band. Test in Task 4.
- **The coach standing in for the status line.** While the figure is up, the status line is gone from VoiceOver but keeps its room, so the card does not jump. The cue is said once. Test in Task 5.
- **The tour at rest.** The tour starts while the clock is idle, when SKIP and the editors are dimmed but showing: it must light SKIP, not skip it. Test in Task 7.
- **A control that changes hands.** FLIP and END share a place: at every state exactly one is in the accessibility tree, and the shutter's spoken name follows the state. Tests in Tasks 2 and 4.
