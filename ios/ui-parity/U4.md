# U4: Menu and Account Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use the `subagent-driven-development` skill (recommended) or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the iPhone app's menu and its You screen have the Android screens' shape: a title and a line saying what the screen is, the rows built from the shared vocabulary, DONE pinned at the foot, the menu full-screen, a badge opening a Cindy sheet, and the avatar drawn as Android draws it.

**Architecture:** the pages' decisions already live in CindyCore (`MenuBuilder`/`MenuPage`, `AccountBuilder`/`AccountPage`, `Avatar`), so this phase changes what SwiftUI draws and, where a word is drawn by the view and not held by the model, moves it into CindyCore with a test that reads it off the Kotlin. The rows are U0's `AvatarRow`, `NavRow`, `InsetGroup`, `BadgeDisc`; the section titles are U3's `SectionTitle`.

**Tech Stack:** SwiftUI (iOS 17.0), CindyCore (XCTest on Linux), XCUITest with `-CindyReplay`.

**Spec:** `ios/ui-parity/PLAN.md` (decisions and global constraints) and `docs/adr/0003-ios-follows-android-ui.md`. The Android sources, read on `origin/main`: `res/layout/activity_menu.xml`, `MenuActivity.kt` (`render`, `settleRowsIn`, the rows' subtitles; not its sheets, which are U5's), `res/layout/activity_account.xml`, `AccountActivity.kt` (`header`, `grid`, `tile`, `showBadge`), `AvatarView.kt`.

## Global Constraints

Everything in the master plan's global constraints, in particular:
- iOS 17.0 is the floor. No blur, no system materials. Colours only from `Palette`, type only from `CindyType` and `Manrope`, icons only from `CindyIcon`.
- Words are copied verbatim from the Kotlin. Nothing in code or comments names a phase.
- **`Ink`, `Color.accent`, `Color.dim`, `Color.warn`, `Chip`, `PrimaryButton` and `GhostButton` stay defined.** The menu's sheets (U5) still read them. This phase stops using them in `MenuScreen.swift`, `AccountScreen.swift` and `AvatarView.swift`.
- The models in CindyCore own the pages and the words they build, and are not changed except for `MenuWords`. The views paint what they say.
- The menu's sheets (movements, body weight, reminder, music, heart rate, Strava, voice), the name sheet and the photo `confirmationDialog` are U5's and stay system sheets and dialogs. This phase presents them as it does today.
- The accessibility identifiers `CindyTrackerUITests` uses keep working; the menu's rows keep their spoken labels (`row.spoken`), which the existing menu tests find them by.
- **UI-test lessons from U2 and U3:** find a control by an identifier or its exact label, never by a fragment another control shares; a covered page stays in XCUITest's queries, so choose the hittable one in code (a query predicate cannot use `isHittable`); a button at the foot of a scroll view exists but is not hittable until scrolled to; the simulator keeps the records earlier tests left unless the launch argument `-attempts ""` empties them for one launch.

## Verification commands

- **Core tests.** `docker run --rm -v "$PWD":/w -w /w swift:6.1.2-noble swift test --package-path ios/CindyCore`, with `--filter <Class>` for one. If Docker is not running in a cloud session: `pkill -9 containerd; pkill -9 dockerd; rm -f /run/containerd/containerd.sock /var/run/docker.pid /var/run/docker.sock; dockerd &`.
- **Parse the app.** `docker run --rm -v "$PWD":/w -w /w swift:6.1.2-noble sh -c 'for f in ios/CindyTracker/*.swift ios/CindyTrackerUITests/*.swift; do swiftc -parse $f || echo FAIL $f; done'`. Syntax only.
- **App tests.** Open the pull request as a draft after Task 1 and read `Build and test the app (macOS)` after pushes; a run takes about 22 minutes and a later push cancels it. Its log lists every failed UI test with its assertion; `gh api repos/alexxgalea/cindy-workout/actions/artifacts/<id>/zip` downloads `ios-captures`.

## Review Focus

- **The largest Dynamic Type size.** At `accessibility-XXXL` a menu row's subtitle wraps instead of clipping, the You screen's three-to-a-row badge titles keep two lines, and DONE, which is pinned, stays on screen on both. Test in Tasks 2 and 3.
- **A menu opened over a live workout.** The Movements row refuses with Android's toast, the footnote says why, and the workout keeps its clock; the rows are dealt in once and do not deal again after a sheet closes. Test in Task 2.
- **A You screen with nothing in it.** No name, no photo, no sessions: the header invites ("Add your name", "Add a photo"), the training line says the badges start with the first session, and every badge is locked with its progress. Test in Task 3.
- **A badge closed without a button.** The dim, a swipe down and the escape gesture do what DONE does: nothing is changed. By construction (the sheet's own rule); owed on a phone.
- **The screen beneath a cover.** The camera under the full-screen menu, and the menu under a pushed screen, are out of the accessibility tree. Owed on a phone.
